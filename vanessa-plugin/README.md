# MCPRagSearch — плагин Vanessa Automation

Внешняя обработка (плагин VA типа «Утилита», или просто внешняя обработка,
открытая в том же сеансе), которая поднимает MCP сервер на внешней компоненте
**http1c** (`libhttp1cWin.dll`): компонента обслуживает **весь MCP-контракт
Ванессы**. Опционально — семантический поиск на Rust-ядре (`rcore.dll`): по
шагам VA (коллекция `vanessa_steps`), по базе знаний VA (коллекция
`vanessa_kb`) и по произвольным файлам из настраиваемых коллекций (таблица
«Коллекции файлов»).

Инструменты MCP не дублируются: плагин вызывает у MCPVA регистрацию всех
инструментов (`ВызватьРегистрациюИнструментовMCP`) через свой фасад, передаёт их
определения в компоненту (`tools_json`), а входящие `ToolCall` диспетчеризует
обратно в обработчики MCPVA. Ответ уходит конвертом
`{"id": ..., "body": "<сериализованный результат MCP>"}` (body — JSON-строка,
двойная сериализация — протокол http1c).

Нужен микро-хук в MCPVA (уже в форке VA): `УстановитьВнешнийФасадМсп` +
`ВызватьРегистрациюИнструментовMCP`. Там же в форке исправлена схема
инструмента `get_data_from_knowledge_base` (`search_string`: number → string —
типизированные клиенты роняли аргумент).

Итого инструментов: 36 инструментов VA + 4 нативных (`search`, `grep`,
`get_segment`, `list_collections` — обслуживаются компонентой без round-trip
в 1С) + `get_search_guide` = **41**.

## Сравнение со штатным поиском (зачем вообще RAG)

Подстрочный поиск против семантического: одни и те же запросы к штатному
`search_for_steps_by_keywords` (подстрока) и к нативному `search` (hybrid, k=5)
по коллекции `vanessa_steps`:

| Запрос | Штатный (подстрока) | RAG (hybrid) |
|---|---|---|
| «нажимаю кнопку» | 16 шагов, **все мимо** («кнопку очистить», «кнопку выбора»), главных нет | ✅ топ-5 = главные шаги: «я нажимаю на кнопку "…"», с именем, в таблице |
| «нажать кнопку» (инфинитив) | **0** | ✅ топ-5 релевантный |
| «click button» (англ. запрос к ru-корпусу) | **0** | ✅ кросс-языковой поиск работает |
| «кнопкa» (опечатка: латинская «a») | **0** | ✅ dense — точный топ (score ≈ 0.88) |
| «заполняю поле и нажимаю кнопку» (составной) | **0**, без намёка, что нужно два шага | ✅ выдача даёт материал по обоим действиям |
| «проверить всплывающее уведомление» (по смыслу) | **0** | ✅ нашло «Если появилось предупреждение…» — попадание при нуле общих слов |
| «выбрать значение из выпадающего списка» | работал (по слову «выпадающ») | ✅ топ чище и ранжирован |
| «кликаю по кнопке» (синоним) | уводил в экзотику (UI Automation) | ✅ закрыто обогащением `embed_text` синонимами действий: dense находит «нажимаю на кнопку» (score ≈ 0.88) |

**Почему подстрока проваливается.** Русская морфология: «кнопка» ≠ «кнопку», и
все шаги вида «нажимаю на кнопку…» по запросу «кнопка» просто не находятся
(5 результатов из 36+ реальных). Порядок слов и предлоги: «нажимаю кнопку» без
«на» давал выдачу, которая *выглядит* успешной, но не содержит ни одного нужного
шага. Ранжирования нет: порядок выдачи не связан с релевантностью, при лимите
обрезка произвольная. Синонимы, инфинитивы, другой язык и опечатки — гарантированный
ноль, потому что сравниваются буквальные байты строки.

**Следствия для ИИ-агента.** Два режима отказа. Нули — агент начинает вручную
подбирать стемы и перечислять падежи через `|` (лишние итерации, лишние токены,
об этом приёме надо ещё догадаться). И опаснее — «успешная» нерелевантная выдача:
агент молча берёт неправильный шаг, и ошибка всплывает только при прогоне
сценария. Семантический поиск закрывает оба: эмбеддинги сводят запрос и шаг по
смыслу независимо от формы слова и языка, а скор даёт честное ранжирование —
6 из 7 провальных кейсов закрылись одним механизмом, седьмой («кликаю») —
обогащением эмбеддингов синонимами при индексации (текст шага в выдаче не
меняется).

**Что ещё закрывает семантический поиск.** Сегментная мета в хитах: `meta.type`
и `meta.lang` шага приходят заполненными, фильтры по ним работают. База знаний —
отдельная коллекция `vanessa_kb`, поиск примеров идёт по ней. Описания коллекций
в `list_collections` — агенту видно, где что искать. По скорам: у hybrid RRF-скоры
≈ 0.03 — это норма, для абсолютных порогов `min_score` используйте режим dense.

## Сборка .epf

Любым стандартным способом сборки из XML-выгрузки, например конфигуратором:

```
1cv8.exe DESIGNER /F <путь_к_базе> /N admin /P admin
    /LoadExternalDataProcessorOrReportFromFiles "vanessa-plugin\MCPRagSearch\MCPRagSearch.xml" "MCPRagSearch.epf"
    /DisableStartupDialogs /Out build.log
```

или `vrunner compileepf` / ibcmd — формат выгрузки тот же, что у плагинов VA
(version 2.10, как `plugins/УтвержденияBDD`).

## Установка

1. Собранный `MCPRagSearch.epf` положить в каталог `plugins/` рядом с
   `vanessa-automation.epf` (VA подхватывает плагины из этого каталога), либо
   открыть как обычную внешнюю обработку в той же сессии, где открыта VA.
2. Компонента — распакованным бандлом, путь к нему указывается на форме:
   1. в группе «Настройки сервера» нажать гиперссылку «Скачать компоненту
      (последний релиз)» — браузер скачает `http1c-addin-full.zip`
      (`libhttp1cWin.dll` + `rcore.dll` + `DirectML.dll`) из последнего релиза
      GitHub (ссылка `releases/latest/download/http1c-addin-full.zip` всегда
      актуальна; страница релизов:
      <https://github.com/DitriXNew/MCP-DB-Client/releases>);
   2. распаковать zip в любой каталог;
   3. нажать «Установить из папки…» и указать этот каталог — плагин проверит
      состав (`libhttp1cWin.dll` обязателен; без `rcore.dll` это lite-бандл, RAG
      недоступен) и подставит каталог в поле «Каталог компоненты»; либо просто
      указать каталог в поле «Каталог компоненты» вручную;
   4. нажать «Запустить».

**Гуард версии.** При подключении плагин читает версию компоненты
(`ПолучитьСтатус` → `version`) и показывает её в поле «Версия». Если в указанном
каталоге бандл старее требуемой (`МинимальнаяВерсияКомпоненты`, сейчас `2.3.0`),
плагин **громко отказывает** и не стартует, а не тихо шлёт старой dll незнакомые
поля — скачайте и распакуйте актуальный бандл.

Требования: Windows x86-64, платформа 8.3.19+ (используются
`НачатьПодключениеВнешнейКомпоненты`, `Выполнить`/`Вычислить` на клиенте).

| Элемент | Назначение |
|---|---|

| Запустить | Подключает компоненту, собирает инструменты из MCPVA, применяет настройки, запускает прослушивание; в режиме RAG — конфигурирует модель и индексирует шаги |

| Обновить статус | Опрашивает компоненту (`ПолучитьСтатус`) и, в режиме RAG, прогресс эмбеддинга (`stats`) |

## Локальная модель (оффлайн)

Поле «Модель» принимает либо **имя из списка**, либо **путь к папке с моделью** —
это два разных режима:

- **Имя из списка** (нужна сеть при первом запуске): модель скачивается
  автоматически в «Каталог моделей» (`cache_dir`). Там fastembed создаёт
  служебный hub-кэш вида `models--intfloat--multilingual-e5-small/`
  (`blobs/` + `snapshots/` + `refs/`) — класть туда файлы руками не нужно,
  и указывать этот каталог как путь к модели **нельзя**: это кэш, а не модель
  (файлы в `snapshots/` — ссылки на блобы, лоадер такой лейаут не понимает).
- **Путь к папке** (оффлайн / air-gapped, сеть не нужна вовсе): файлы читаются
  напрямую с диска. Папка должна содержать ровно пять файлов:

  ```
  <папка модели>\
  ├── onnx\model.onnx           ← ONNX-модель (допускается и model.onnx прямо в корне)
  ├── tokenizer.json
  ├── config.json
  ├── special_tokens_map.json
  └── tokenizer_config.json
  ```

  Где взять: страница модели на Hugging Face — та же, что открывает
  гиперссылка на форме, например
  <https://huggingface.co/intfloat/multilingual-e5-small/tree/main>:
  четыре json-файла из корня репозитория + `onnx/model.onnx` (fp32, ~470 МБ
  для e5-small). Квантованный вариант (int8, ~118 МБ, заметно быстрее на CPU)
  кладётся **под тем же именем**: лоадер ищет только `onnx/model.onnx` или
  `model.onnx`, поэтому `model_quantized.onnx` и подобные надо переименовать.

Типичные ошибки: указать в «Модель» каталог hub-кэша (`models--…`) или папку,
где ONNX лежит под другим именем — в обоих случаях запуск RAG упадёт с ошибкой
загрузки модели. «Каталог моделей» на режим «путь к папке» не влияет — он
используется только при скачивании модели по имени.

## Коллекции

В режиме `MCP+RAG` плагин индексирует три типа коллекций (порядок индексации:
шаги → база знаний → коллекции файлов):

| Коллекция | Содержимое |
|---|---|
| `vanessa_steps` | Все шаги VA, один чанк = один шаг. Текст хита = готовый текст шага; в `meta` хита: `meta.type` = категория шага, `meta.lang` = язык генератора Gherkin. `embed_text` обогащается категорией шага (запрос «шаги для работы с таблицами» находит шаги и по имени категории) и синонимами действий («кликаю»/«click» семантически ложатся на «нажимаю» и т.п.) — текст шага в выдаче не меняется, обогащается только эмбеддинг |
| `vanessa_kb` | База знаний VA (макет `БазаЗнанийДляMCP`, 98 вопросов-ответов «как правильно писать сценарии»): сегмент = вопрос + ответ, `meta.type` = `qa`, `meta.num` = номер вопроса |
| файловые | Произвольные текстовые файлы из таблицы «Коллекции файлов» (см. ниже) |

### Память

Память ест не индекс, а **сессии модели эмбеддинга**: каждая сессия — отдельная
копия модели в RAM (e5-small fp32 ≈ 0.5 ГБ весов + рабочая память onnxruntime,
итого до ~1–1.5 ГБ на сессию под нагрузкой). Сам индекс крошечный: вектор
сегмента — 384 числа (~1.5 КБ), тексты шагов — мегабайты.

Поле **«Потоки индексации»** управляет числом bulk-сессий: по умолчанию `1`
(одна сессия индексации + одна сессия поиска — ожидаемое потребление
**~1.5–2 ГБ**), `0` — на усмотрение компоненты (половина ядер, максимум 4 —
быстрее на больших корпусах, но каждая сессия добавляет копию модели в RAM),
`N` — ровно N сессий.

После завершения индексации (статус «Готово») плагин вызывает `trim_memory` —
bulk-сессии выгружаются и память возвращается системе; остаётся только
query-сессия для поиска. При следующей (пере)индексации ядро пересоздаёт
bulk-сессии автоматически (несколько секунд на загрузку модели с диска).

Кнопка **«Остановить»** (и закрытие формы плагина) вызывает `reset` ядра:
коллекции и все сессии модели выгружаются, память возвращается ОС. Ядро —
синглтон внутри процесса 1С, поэтому без явного `reset` оно держало бы индекс
и сессии до завершения процесса; `reset` освобождает память сразу при остановке.

Жёсткого лимита памяти у ядра нет: при настоящем исчерпании RAM процесс 1С
упадёт (аллокация в Rust не «ловится»). Существующие предохранители: файлы
больше 5 МБ пропускаются при индексации; инференс-батч фиксирован небольшим
(32 текста на сессию) — пиковая рабочая память onnxruntime растёт как
батч × длина² последовательности, её арена не возвращается ОС, пока жива
сессия, и при батче 32 высшая точка держится в районе ~1 ГБ на сессию
(скорость на CPU от уменьшения батча практически не меняется).

### Чистота коллекций (reset)

Ядро живёт в процессе 1С дольше формы плагина: остановка/запуск MCP-сервера
не выгружает `rcore.dll`. Поэтому каждая (пере)индексация начинается с `reset`:
ядро очищается целиком, и коллекции, переименованные или удалённые из таблицы
«Коллекции файлов», не накапливаются от запуска к запуску — коллекций-сирот от
прошлых запусков не остаётся.

### Вотчер актуальности

Раз в 30 секунд плагин сверяет язык генератора Gherkin и размер библиотеки
шагов с состоянием на момент индексации; при расхождении (сменили язык,
подключили/перечитали библиотеки шагов) автоматически запускает
переиндексацию. Вотчер работает, пока сервер запущен в режиме `MCP+RAG`.

## Коллекции файлов

Таблица «Коллекции файлов» в группе «Семантический поиск (RAG)» позволяет, кроме
шагов VA, проиндексировать произвольные текстовые файлы — например, фича-файлы
проекта. Каждая строка таблицы — отдельная коллекция в `rcore`; индексация
выполняется при запуске в режиме `MCP+RAG` и по кнопке «Переиндексировать»
(после шагов, до опроса статуса).

Колонки:

| Колонка | Назначение |
|---|---|
| Коллекция | Имя коллекции (желательно латиница/цифры/подчёркивание, например `project_features`) — под этим именем коллекция видна MCP-инструментам |
| Описание | Описание коллекции для ИИ-агента — уходит в `collection_description` и попадает в описание инструментов поиска |
| Каталог | Папка с файлами; сканируется рекурсивно (включая подпапки) |
| Расширения | Фильтр расширений: `feature`, `feature;md;txt`, допускается и форма `*.feature`; пусто = `feature` |

Каждый файл индексируется целиком одним вызовом `index_raw` (`doc_id` — полный
путь, `name` — имя файла, `meta.path`/`meta.ext`): ядро само режет текст на
чанки (~300 токенов, по границам строк). Для `.feature`-файлов плагин
дополнительно передаёт три параметра `chunk_cfg`, чтобы чанк был ровно одним
сценарием Gherkin:

- `boundary_regex` — ключевые слова Gherkin («Сценарий:», «Структура
  сценария:», `Scenario:`, «Функционал:» и т.д.): строка по этой границе всегда
  начинает новый чанк, перекрытие через границу не переносится, поэтому хит
  поиска — осмысленный кусок ровно одного сценария, а не склейка хвоста одного
  с началом другого. («Примеры:»/`Examples:` границей не считаются — таблицы
  примеров остаются при своей структуре сценария.)
- `boundary_lead_regex` — ведущие `@теги` и `#комментарии` сценария уходят
  внутрь чанка этого сценария, а не остаются в предыдущем.
- `prepend_header` — заголовок фичи (`Функционал:`/`Feature:` с описанием и
  блоком `Контекст`/`Background` над первым сценарием) подмешивается в
  **эмбеддинг** каждого сценария, восстанавливая контекст фичи. Текст хита и
  диапазоны строк при этом не меняются — `grep`/`get_segment` отдают чистый
  исходник.

Для коллекции работают все поисковые инструменты —
`search` (семантический поиск), `grep` (регулярные выражения) и `get_segment`
(чтение фрагмента файла по строкам, с контекстом до/после). Файлы читаются в
UTF-8; файлы больше 5 МБ пропускаются с сообщением. Строки таблицы без имени
коллекции или каталога пропускаются, перед заливкой коллекция пересоздаётся
(`delete_collection`).

Пример: коллекция `irp_features`, описание «Фича-файлы проекта ИРП (Gherkin,
русские шаги)», каталог `D:\Projects\IRP\features`, расширения `feature` — после
индексации ИИ-агент через MCP ищет по содержимому всех фич проекта семантически
(`search`), по регулярке (`grep`) и читает найденные места из файлов
(`get_segment`).

## Промпты и скил поиска

Кроме инструментов, сервер публикует один MCP-промпт (`prompts_json`
компоненты):

| Промпт | Назначение |
|---|---|
| `search-guide` (title «Vanessa: как искать шаги (RAG)») | Инструкция для ИИ-агента: как искать шаги, примеры и правила Vanessa Automation через семантический поиск (`list_collections`, `search`, `grep`, `get_segment`) |

Текст хранится в текстовом макете `СкилПоиска` (правится в конфигураторе) и
описывает весь рабочий процесс: подбор шагов по коллекции `vanessa_steps`
(режим dense), вопросы к базе знаний `vanessa_kb`, поиск примеров по файловым
коллекциям (`grep` / `get_segment`) и частые ошибки. Аргументов у промпта нет;
запрос `prompts/get` обслуживается событием `PromptGet` (ответ —
`{"messages":[{"role":"user","content":{"type":"text","text":"..."}}]}`
тем же конвертом `{id, body}`; для совместимости принимается и старое имя
`search_guide`).

Тот же текст отдаёт инструмент-дубль **`get_search_guide`**: не все клиенты
показывают MCP-промпты (известный случай — VS Code через `mcp-remote`), а
инструменты агент видит всегда — поэтому скил доступен обоими путями.

MCP-клиенты показывают промпты как slash-команды: например, в Claude Code это
`/mcp__vanessa__search-guide` (префикс зависит от имени сервера в конфигурации
клиента) — вызов вставляет текст инструкции в контекст диалога перед
написанием сценария.

## Подключение MCP-клиента

```json
{
	"mcpServers": {
		"vanessa": {
			"type": "http",
			"url": "http://localhost:8765/mcp"
		}
	}
}
```

В режиме RAG поисковые инструменты (`search` / `grep` / `get_segment` /
`list_collections`) обслуживаются самой компонентой без round-trip в 1С — по
коллекциям `vanessa_steps`, `vanessa_kb` и по всем коллекциям файлов из
таблицы.

## Если RAG «не видит» rcore.dll (rag_not_installed / rag_load_failed)

`rcore.dll` статически зависит от `DirectML.dll` и рантайма Visual C++. Ошибки
различаются по коду:

- **`rag_not_installed`** — `rcore.dll` действительно нет рядом с
  `libhttp1cWin.dll` (lite-бандл). Доустановите полный бандл — подхватится без
  перезапуска 1С.
- **`rag_load_failed` (Win32 error N)** — файл на месте, но не загрузился;
  код ошибки и подсказка приходят в сообщении, а также видны в
  `GetStatus` (`rag_available` / `rag_load_error`):
  - **126** — не найдена зависимость: `DirectML.dll` должен лежать в одном
    каталоге с `rcore.dll` (компонента ищет зависимости рядом с ним), и на
    хосте должен быть установлен VC++ runtime (`vcruntime140.dll`,
    `vcruntime140_1.dll`, `msvcp140.dll` — [VC++ Redistributable x64](https://aka.ms/vs/17/release/vc_redist.x64.exe));
  - **193** — битность: всё должно быть x86-64;
  - **1114** — зависимость не инициализировалась (несовместимый
    `DirectML.dll` для этой версии Windows).

Классический случай — **Windows Server 2019**: в нём нет системного
`DirectML.dll` (появился в Windows 10 1903), поэтому работает только бандловый.
Бандл кладёт официальный редистрибьютив DirectML (поддерживает Windows 10
1709+ включая Server 2019), а компонента ищет зависимости в каталоге
`rcore.dll` — на новых Windows это же место просто выигрывает у System32.
